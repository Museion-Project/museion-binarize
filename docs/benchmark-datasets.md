# Benchmark datasets and profiles

Two versioned TOML manifest formats drive a benchmark: a **dataset**
(what to measure) and a **profile** (what settings to measure it with).
See [`benchmark-metrics.md`](benchmark-metrics.md) for what the
resulting numbers mean and [`benchmark-running.md`](benchmark-running.md)
for how to actually invoke a benchmark.

## Dataset manifest: `museion-binarize-benchmark-dataset` v1.0

```toml
schema = "museion-binarize-benchmark-dataset"
schema_version = "1.0"

id = "synthetic-document-v1"
title = "Synthetic document binarization benchmark"
description = "..."
license = "CC0-1.0"
provenance = "Generated by museion-binarize-core's benchmark_fixtures module ..."
ground_truth_method = "Ground truth is the exact procedural shape drawn before any degradation is applied ..."
ground_truth_polarity = "black_is_zero"   # optional, default shown

[[pages]]
id = "clean-body-text"
input = "input/clean-body-text.png"
ground_truth = "ground-truth/clean-body-text.png"
category = "text"
tags = ["example"]

[[pages.rois]]
id = "example-roi"
x = 10
y = 10
width = 20
height = 20
tag = "diacritic"
```

Required dataset-level fields: `schema`, `schema_version`, `id`,
`title`, `license`, `provenance`, `ground_truth_method`. `description`
is optional (defaults to empty). Required page fields: `id`, `input`,
`ground_truth`, `category`. Optional page fields: `tags`, `notes`,
`source_url`, `rights_holder`, `expected_width`, `expected_height`,
`rois`.

### `ground_truth_polarity`

`"black_is_zero"` (default) or `"black_is_255"` — which raw pixel value
(`0` or `255`) a ground-truth PNG uses for foreground/ink. This is
purely a file-reading convention; the project-internal `BinaryMask`
convention (`true` = black) is unaffected either way — see
[`benchmark-metrics.md`](benchmark-metrics.md#polarity).

### Ground truth review metadata (optional)

`ground_truth_creator`, `ground_truth_review_status`,
`ground_truth_review_method` — free-text fields for documenting how
ground truth for a real (non-synthetic) dataset was produced and
reviewed. See "Real scholarly corpus plan" below for the intended
workflow these fields support.

## Path safety: dataset-root containment

Every `input`/`ground_truth` path is resolved **relative to the
manifest's own directory** (the "dataset root") and, after
canonicalization, is required to remain **inside** that root. This
rejects both `../../secret`-style traversal and a symlink that points
outside the root — a dataset manifest is untrusted input (it may name a
path a user points the CLI at), so this is checked unconditionally, not
just for committed datasets. See
`crates/museion-binarize-core/src/benchmark/dataset.rs`'s
`resolve_contained` and its traversal/symlink-escape tests.

There is no "local external dataset" mode that relaxes this: a dataset
pointed at from anywhere on disk (`--dataset /path/to/local/dataset.toml`)
still has every page path resolved and contained under *that* dataset's
own directory — only the dataset root itself may be anywhere, not the
files it references relative to it.

## Resource limits

Untrusted manifest input is bounded (see
`crates/museion-binarize-core/src/benchmark/limits.rs`): at most 10,000
pages per dataset, 20,000px per image dimension, 200,000,000 pixels per
image, 64 ROIs per page, 256 runs per profile. A manifest exceeding any
of these is rejected with a structured `ResourceLimitExceeded` error
before any allocation proportional to the declared (not yet verified)
size happens.

## Licensing and provenance — what may be committed

Every committed dataset must have explicit `license` and `provenance`
fields, and `ground_truth_method` describing how ground truth was
produced. Preferred license for synthetic material is `CC0-1.0`.

**Do not commit**: scans copied from Google Books, Internet Archive
derivatives without rights review, modern critical-edition apparatus
pages, copyrighted book pages, random screenshots, pages extracted from
commercial databases, or proprietary OCR datasets. A public-domain
*text* does not automatically mean a modern *scan or edition* of it is
unrestricted — the scan/edition itself can carry its own rights. If in
doubt, do not commit the material; see `test-data/README.md` and
`CONTRIBUTING.md` for the project-wide rule this follows.

### Why no real fonts

`synthetic-document-v1`'s `synthetic_diacritic_detail` category uses
procedural geometric shapes (short strokes, arcs, dots) rather than
actual polytonic Greek diacritics rendered from a real font. This is
deliberate, in order of preference the milestone specification set out:

1. Commit generated ground truth whose provenance is clear and
   reproducible (what this suite does).
2. Use a permissively licensed font through a reviewed package/license
   — not done in this milestone.
3. Procedural stroke/glyph-like shapes when deterministic font
   rendering cannot be guaranteed — what this suite does.

A committed "golden" raster generated from a system font would not be
reproducible: different machines have different fonts installed, and
CI cannot be assumed to have any specific one. Redistributing a font
binary merely for convenience is also not something this project does.
See `test-data/benchmark/synthetic-v1/README.md` for this category's
exact limitations.

## Region of interest (ROI)

An ROI is a rectangular crop, in the same pixel coordinate system as
the page (top-left origin), with an optional `tag` used for
cross-page aggregation (see `benchmark-metrics.md`'s macro/micro
discussion — the same aggregation logic applies per ROI tag). Bounds are
validated against the page's actual dimensions before any metric runs
— an out-of-bounds ROI is a structured `InvalidRoi` error, never
silently clamped or cropped, since a silently-adjusted region would no
longer be the region the dataset author actually meant to measure.

### Why ROIs matter

A page can score `F1 = 0.995` overall while losing every tiny breathing
mark, if those marks are only a tiny fraction of total foreground
pixels — whole-page F1 alone cannot see that. ROI tags (e.g.
`diacritic`, `apparatus`) let the benchmark report standard metrics
*within* a small tagged region, separately from the whole page, which is
scientifically much cleaner than inventing a single ad hoc "Greek
score." See `docs/benchmark-results/synthetic-v1.md` for what the
`diacritic`/`apparatus` ROI aggregates currently show (and do not yet
show) on this suite.

## Profile manifest: `museion-binarize-benchmark-profile` v1.0

```toml
schema = "museion-binarize-benchmark-profile"
schema_version = "1.0"
id = "default-method-comparison"

[[runs]]
id = "otsu-300"
dpi = 300
method = "otsu"

[[runs]]
id = "sauvola-300-default"
dpi = 300
method = "sauvola"
window_size = 25
k = 0.2

[[runs]]
id = "manual-300-180"
dpi = 300
method = "manual"
threshold = 180
```

`method` is `"otsu"`, `"sauvola"`, or `"manual"`. Fields not applicable
to the chosen method must be absent — `k`/`window_size`/`dynamic_range`
only for `sauvola`, `threshold` only for `manual` (required there),
`background_radius` only alongside `background_normalization = true` —
enforced by the same discipline `SettingsArgs::to_settings` already
applies to CLI flags (see `docs/cli.md`), so a profile can never
silently ignore a parameter typo'd against the wrong method. Every run
is validated (including full range validation via
`ProcessingSettings::validate`, the exact function
`process`/`analyze`/`estimate` already use) at load time, not partway
through a benchmark run.

For the raster benchmark level, `dpi` is **metadata only** — it has no
effect on processing, since there is no PDFium rendering step to choose
a DPI for. It is recorded in the report for context and for future use
by a PDF-level (Level B) benchmark.

### Why profiles enumerate runs explicitly

A profile is a fixed, explicit list, not a combinatorial sweep
generator — deliberately, so a profile file can never accidentally
expand into an unbounded number of benchmark runs. Want to compare
three Sauvola `k` values? Write three `[[runs]]` entries. This also
means a profile fully documents, by itself, exactly what was compared —
no separate sweep-configuration file to keep in sync.

## Reproducibility digests

A `LoadedDataset`/`LoadedProfile` exposes SHA-256 digests of its own
manifest bytes (`manifest_digest`/`digest`) and, for a dataset, of every
referenced input/ground-truth file
(`page_file_digests`). The benchmark report includes the manifest
digests so a result can be tied to the exact bytes that produced it —
see `docs/benchmark-running.md`, "Reproducibility digests," for how
this appears in a report.

## Real scholarly corpus plan (not populated in this milestone)

`synthetic-document-v1` validates the framework; it is not a
representative corpus of real scanned or printed material. A future,
rights-cleared corpus would need, per sample: rights/provenance,
edition/publication, scan source, page identifier, and a documented
ground-truth production protocol along these lines:

```
high-quality source raster
-> initial segmentation
-> manual correction at pixel level
-> independent review
-> lock ground truth
-> checksum
```

Ground truth produced only by running an automatic thresholding tool
(including this project's own) on the source, without human
verification, would not satisfy this — see
`docs/benchmark-metrics.md` on why ground truth produced by the system
under test would make the benchmark circular. Categories such a corpus
would eventually want to cover: clean modern Greek typography, older
letterpress Greek, small critical apparatus, polytonic dense accents,
faded scans, uneven illumination, microfilm/reproduction artifacts, and
mixed Latin/Greek/apparatus pages. None of this material is committed
to this repository in this milestone.
