# 统一桌面工作区：本机闭环完成

按用户“做可用闭环”“充分的UI设计权限”“工具逻辑和使用动线清晰一致”“OCR入口一起做但暂不开放”的要求，当前主界面已统一为：打开 PDF → 选择黑白处理与/或目录书签 → 预览、编辑、整份复核 → 保存新 PDF。意图对齐为 `aligned`，依据 `intent.md §8.36 DW1–DW5`。本次仅为授权的本机实现与验证；没有发布、云调用、模型下载或开启后台任务。

## 可直接使用

本地应用：`target/debug/bundle/macos/Museion Binarize Local.app`。双击打开；内置前端、PDFium及目录脚本，不需要运行开发服务器。它是本机构建的调试版，未签名、未公证，未声明可移植发行就绪。

左侧选择处理工具；中间翻页并比较原页/黑白效果；右侧生成后可改标题、层级、PDF目标页、增删和撤销，也能返回带位置框的目录原页。目录页与目标页都明确使用 PDF 物理页码。无页码章题可选择保留；保留时需要填写目标页。只有整份目录确认且目标/树有效后才能保存。黑白处理与目录可分别使用，合用只产生一个新 PDF。已有目标文件会拒绝覆盖。OCR正文识别入口固定可见且禁用。

本机依赖：目录功能使用已有 Python + PyMuPDF + Pillow；图像目录使用 macOS Vision，首次运行还需要 Swift 编译器。当前机器已具备。没有安装这些依赖的其他电脑尚未验证。目录自动结果仍需复核，尤其扫描文本标题、漏号与映射；“已填写目标”并不等于自动正确。

生成目录、编辑标题、撤销、调整父节点、改目标、增删、返回源页、整份确认和保存使用真实原生应用连接；测试仅以开发夹具提供系统文件选择器的固定路径。首轮夹具未生效、选择器打开了另一文档，该失败轮未纳入三书验收。修正后固定Menn并验证文件名。第二轮脚本的300秒保存等待超时，当时真实作业仍在第108页；作业没有被中止，最终由 `native-saved.png`、生产保存回执与独立PDF重开确认成功。`native-ui-test-final.js`已将等待限额改为整本处理所需范围，但没有为此重复耗时的全书黑白处理。不得把该超时日志改写为脚本全程无错。

## 修正与验证边界

- Native Brisson有断行，原层级状态可能回指已闭合分支。现在保留该父节点解释为候选，将有效输出标为待复核，保证源顺序树可编辑；不挪动源行来隐藏错误。该native路径的标题分组仍弱，图像读取可由用户明确选择。
- 接线首轮误用PyMuPDF完整页渲染，Brisson仅29个导航条目；定位渲染差异后恢复既有PDFium输入，当前为31项。保留了失败产物，未把旧冻结Vision成绩当作新提取路径成绩。
- Apple Vision在工具沙箱中失败时，原适配器报出缺失字段。现在显示真实本机识别错误；合法空页得到零数字crop。实际Vision验证在本机执行。
- MuPDF保存会调整字典键顺序。writer现在允许这种无语义变化，但仍逐一比较完整键集合与每个值，流字节不变；改变页面值的反例会被拒绝。
- 文件/会话过期、重复操作、非法目标、循环父节点、来源注入、取消与输出碰撞均有相应约束；修改出错时保留当前目录草稿。取消等待当前本地步骤结束。

验证：57个前端测试、45个桌面后端测试、57个书签core单元测试、26个既有compiler集成测试、22个Python合同测试，共207项通过；TypeScript/build/lint通过。最终app内的脚本与源码哈希一致，PDFium一致，生产前端不含测试文件选择器。旧四页compiler输出逐字段一致（18/11/32个源节点，18/11/31个导航节点）；原55/60联合结果仅作为冻结重放参照。728个旧证据/Gold/raw/geometry保护文件哈希全部不变。

当前仍未证明：新书泛化、独立人工复核后的准确率与耗时、无Python依赖的可移植安装包、完整打包应用中的三书端到端回归。原生闭环证据来自开发应用；本地包完成构建、资源一致性及启动检查，未宣称发行验收。OCR算法、Surya、Gold和provider配置没有改变。
